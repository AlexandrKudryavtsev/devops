# 11. DaemonSet: агент на каждом подходящем узле

## Какую проблему решает DaemonSet

Deployment поддерживает заданное количество экземпляров приложения. Но сборщику журналов или агенту мониторинга нужно присутствовать на каждом обслуживаемом узле. Три агента на одном Node не заменяют по одному агенту на трёх Node.

**DaemonSet описывает правило: на каждом подходящем узле должен работать один его Pod.**

Речь о Pod конкретного DaemonSet. На том же узле могут работать Pod других DaemonSet и приложений.

| Контроллер | Главный вопрос |
|---|---|
| Deployment | Сколько экземпляров приложения нужно поддерживать? |
| DaemonSet | На каких узлах нужен экземпляр агента? |
| Job | Сколько успешных завершений нужно получить? |

## Механизм

```text
условия размещения + существующие Node
                   ↓
         набор подходящих узлов
                   ↓
  по одному Pod DaemonSet на каждом из них
```

Количество Pod здесь — **следствие выбора узлов**. У DaemonSet нет `spec.replicas`: если подходящих узлов стало больше, потребуется больше Pod, даже если объект DaemonSet не менялся.

Контроллер сравнивает нужный набор с фактическим: создаёт недостающие Pod и убирает свои Pod с узлов, которые перестали подходить.

```text
Deployment → ReplicaSet → Pod
DaemonSet               → Pod
```

DaemonSet создаёт Pod напрямую. Для каждого он задаёт ограничение на конкретный целевой узел; Scheduler назначает Pod этому узлу, а kubelet обеспечивает запуск контейнеров. Узел — место запуска, владелец Pod — DaemonSet. Подробнее — [размещение Pod DaemonSet](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/#how-daemon-pods-are-scheduled).

## Как читать манифест

В примере агент нужен на Node с меткой `monitoring=enabled`:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
  namespace: study
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      nodeSelector:
        monitoring: enabled
      containers:
        - name: agent
          image: busybox:1.36
          command: ["sh", "-c", "while true; do sleep 3600; done"]
```

BusyBox — учебная замена долгоживущему агенту. Здесь важен способ размещения; в реальном приложении контейнер выполнял бы сбор журналов или мониторинг.

Три части описания отвечают за разные решения:

| Поле | Смысл |
|---|---|
| `spec.selector` | По каким меткам выбирать управляемые **Pod** |
| `spec.template` | Какими должны быть создаваемые **Pod** |
| `spec.template.spec.nodeSelector` | Какие **Node** подходят для размещения |

**Selector Pod и selector узлов работают с метками разных объектов.** `app=node-agent` стоит на Pod, а `monitoring=enabled` должно стоять на Node. Метки не копируются между ними.

Как у Deployment из записи 2, метки шаблона Pod должны соответствовать `spec.selector`. Владение записано отдельно в `ownerReferences`; совпадение меток само по себе не означает владение.

DaemonSet и его Pod принадлежат namespace `study`, а Node — ресурсы уровня кластера. Namespace не выделяет DaemonSet отдельный набор физических узлов.

`nodeSelector` — один из способов задать подходящие узлы. Другие ограничения размещения тоже учитываются; их подробности относятся к теме планирования.

## Что происходит при изменениях

| Изменение | Реакция Kubernetes |
|---|---|
| Появился новый подходящий Node | DaemonSet создаёт Pod для этого узла |
| Node потерял нужную метку | DaemonSet убирает свой Pod с него |
| Pod удалён, Node по-прежнему подходит | DaemonSet создаёт новый Pod для того же узла |
| Завершился процесс в контейнере | Kubelet перезапускает контейнер внутри того же Pod |

Последние два случая продолжают различие из записи 9: **замена Pod контроллером и перезапуск контейнера kubelet — разные действия**. Для Pod DaemonSet используется `restartPolicy: Always`, поэтому завершение процесса не засчитывается как достигнутая цель Job.

Если подходящих узлов нет, правильное желаемое количество Pod равно нулю. Контроллер восстанавливает экземпляр, только пока этот экземпляр нужен по правилу размещения.

Реакция на потерю метки — работа контроллера DaemonSet. Обычный уже размещённый Pod не удаляется автоматически только потому, что Node перестал соответствовать его `nodeSelector`. См. [реакцию DaemonSet на метки](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/#updating-a-daemonset) и [правила размещения](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/#node-affinity).

## Изменение набора узлов и обновление шаблона

Здесь важно различие, знакомое по масштабированию и rollout:

| Что изменилось | Что меняется у агента |
|---|---|
| Метки Node или состав узлов кластера | Где и сколько экземпляров требуется |
| Образ, команда или другое поле `spec.template` | Конфигурация создаваемых экземпляров |

Новый подходящий узел получает Pod по прежнему шаблону. Это не новая версия DaemonSet: его `spec.template` не менялся.

Изменение шаблона создаёт новую ревизию. При `RollingUpdate`, стратегии по умолчанию, контроллер заменяет старые Pod новыми на подходящих узлах. Как в записи 6, изменение команды запускает обновление даже при прежнем образе. Поле `nodeSelector` тоже находится внутри шаблона, поэтому его изменение — изменение `spec.template`.

«Один Pod на узел» — цель устойчивого состояния. Настройки обновления определяют, будет ли на узле пауза между версиями или временно будут соседствовать старый и новый Pod. См. [обновление DaemonSet](https://kubernetes.io/docs/tasks/manage-daemon/update-daemon-set/).

## Желаемый набор и готовность — разные вещи

У Deployment число реплик задано в `spec`. У DaemonSet число нужных экземпляров вычисляется из правил размещения и узлов. В выводе `get daemonset` оно показано как `DESIRED`:

| Колонка | Что показывает |
|---|---|
| `DESIRED` | На скольких узлах нужен Pod этого DaemonSet |
| `CURRENT` | На скольких таких узлах уже есть его Pod |
| `READY` | На скольких таких узлах есть готовый Pod |

Например, `DESIRED=3, CURRENT=3, READY=2` означает: агент нужен на трёх узлах, Pod присутствуют, но готовность подтверждена лишь на двух. Создание Pod ещё не означает готовность приложения — как в записях 2 и 9.

`DESIRED=0, READY=0` может быть правильным состоянием: ни один узел не подходит. Сначала проверяют **какой набор требуется**, затем **достигнут ли он**. Определения счётчиков есть в [DaemonSetStatus](https://kubernetes.io/docs/reference/kubernetes-api/apps/daemon-set-v1/#daemonsetstatus).

## Основные команды

```bash
# Узлы и метка, по которой их выбирают
kubectl get nodes -L monitoring

# Требуемый набор и размещение фактических Pod
kubectl get daemonset node-agent -n study
kubectl get pods -n study -l app=node-agent -o wide

# Причина расхождения с желаемым состоянием
kubectl describe daemonset node-agent -n study
kubectl describe pod POD -n study
kubectl logs POD -n study --tail=50

# Применение и проверка обновления шаблона
kubectl apply -f node-agent.yaml
kubectl rollout status daemonset/node-agent -n study --timeout=60s
kubectl rollout history daemonset/node-agent -n study
```

`-L` добавляет метку Node в колонки, `-l` выбирает Pod по меткам, `-o wide` показывает их узлы. `node-agent.yaml` — файл с манифестом из примера.

При диагностике двигайся по модели: подходящие узлы → требуемые Pod → фактические Pod → готовность контейнеров. Если `DESIRED` неожиданно равен нулю, начни с правил выбора узлов; если Pod есть, но не готов, используй инструменты из записи 3.

## Проверь себя

**1. В кластере три узла, подходят только два. Сколько Pod нужно DaemonSet? Можно ли заменить их двумя Pod на одном узле?**

<details>
<summary>Показать ответ</summary>

Нужно по одному Pod на каждом из двух подходящих узлов. Два Pod на одном узле не выполняют правило для другого. Важны и количество, и размещение.

</details>

**2. На Node поставили `app=node-agent`, но не `monitoring=enabled`. Подходит ли он для примера?**

<details>
<summary>Показать ответ</summary>

Нет. Условие выбора Node — `monitoring=enabled`. `app=node-agent` используется selector Pod; одинаковая метка на другом типе объекта не выполняет это условие.

</details>

**3. Контейнер завершился, а затем весь Pod удалили. Кто восстанавливает работу в каждом случае?**

<details>
<summary>Показать ответ</summary>

Kubelet перезапускает контейнер в том же Pod благодаря Always. После удаления Pod DaemonSet создаёт новый для узла, если тот по-прежнему подходит.

</details>

**4. Единственный подходящий узел потерял нужную метку. Должен ли DaemonSet бесконечно восстанавливать свой Pod?**

<details>
<summary>Показать ответ</summary>

Нет. Изменился требуемый набор: подходящих узлов теперь ноль. DaemonSet уберёт свой Pod с этого узла.

</details>

**5. Появился новый подходящий узел, а позже изменился image в шаблоне. В каком случае появляется новая ревизия?**

<details>
<summary>Показать ответ</summary>

При изменении image в spec.template. Для нового узла создаётся экземпляр прежнего шаблона; при изменении шаблона начинается обновление при RollingUpdate.

</details>
