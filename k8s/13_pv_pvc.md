# 13. PV и PVC: как сохранить данные при замене Pod

## Какую проблему решаем

В [записи 12](12_volumes.md) мы разобрали общий механизм: Pod объявляет volume, а контейнер подключает его через `volumeMounts`. `emptyDir` сохраняет файлы при перезапуске контейнера, но теряет их вместе с Pod. Для базы данных этого недостаточно: замена Pod должна получить ранее записанные данные.

**Постоянное хранилище отделяет жизненный цикл данных от жизненного цикла Pod.** Здесь разберём отдельный PVC, связанный с PV: после удаления Pod запрос и хранилище остаются, и новый Pod может подключить их снова. Удаление самого PVC — другое событие, последствия которого рассмотрим ниже.

## Механизм: запрос и предоставленное хранилище

**PersistentVolumeClaim (PVC) — запрос приложения на хранилище; PersistentVolume (PV) — ресурс Kubernetes, представляющий предоставленное хранилище.** Приложение описывает нужный объём и свойства через PVC, а инфраструктура предоставляет подходящий PV. Так Pod может использовать постоянные данные, не описывая в своём шаблоне конкретный облачный диск или адрес сервера хранения.

```text
контейнер → mountPath → volume Pod → PVC ↔ PV → реальное хранилище
                                      запрос  предоставленный ресурс
```

| Понятие | Ответственность | Область |
|---|---|---|
| Pod | Выполнять приложение и объявлять используемые volumes | Namespace |
| PVC | Запрашивать хранилище с нужными свойствами | Namespace |
| PV | Представлять диск, сетевой том или другое предоставленное хранилище | Кластер |
| StorageClass | Описывать класс хранилища и способ его динамического предоставления | Кластер |

Pod из `study` использует PVC из `study`; PV и StorageClass namespace не имеют. Связь PVC с PV — **один к одному**: связанный PV не выдаётся одновременно другому PVC. Несколько Pod могут использовать один PVC, если это допускают режим доступа и система хранения.

Когда запрос удовлетворён, PVC и PV получают состояние `Bound`. Это связь объектов, а не две копии файлов: сами данные находятся в системе хранения, представленной PV. В etcd сохраняется описание ресурсов Kubernetes, а не содержимое диска приложения.

## Как подключить PVC к контейнеру

В примере из [записи 12](12_volumes.md) источником volume был `emptyDir`; здесь используется `persistentVolumeClaim`. Механизм подключения тот же: `spec.volumes` у Pod и `volumeMounts` у контейнера. Сохрани следующий пример как `storage-demo.yaml`: первый объект запрашивает хранилище, второй подключает его к учебному контейнеру.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-data
  namespace: study
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: storage-demo
  namespace: study
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "while true; do sleep 3600; done"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: database-data
```

BusyBox знаком по записи 8: здесь он позволяет записать файл и проверить его после замены Pod. Для автоматического предоставления хранилища в этом примере нужен работающий provisioner и StorageClass по умолчанию; если их нет, потребуется подходящий заранее созданный PV или явный выбор существующего класса.

| Поле | Что означает |
|---|---|
| `accessModes` | Требуемые режимы доступа к тому |
| `resources.requests.storage: 2Gi` | Минимальный требуемый объём; подходящий PV может быть больше |
| `volumes[].name: data` | Имя volume внутри Pod |
| `persistentVolumeClaim.claimName: database-data` | Имя PVC в namespace Pod |
| `volumeMounts[].name: data` | Какой объявленный volume подключить контейнеру |
| `mountPath: /data` | Где контейнер увидит файловую систему тома |

**Имена в `volumes` и `volumeMounts` должны совпадать, а имя PVC задаётся отдельно в `claimName`.** PVC сам по себе не создаёт папку внутри контейнера: нужно описать обе части подключения. Приложение также должно писать именно в `/data`; файл, записанный вне подключённого volume, не становится постоянным только из-за наличия PVC.

В примере используется режим тома `Filesystem`, который применяется по умолчанию. Есть и `volumeMode: Block`: он предоставляет сырое блочное устройство через `volumeDevices`, а не папку через `volumeMounts`. Это отдельный способ использования хранилища; наш пример проверяет обычные файлы. См. [режимы томов и связывание PV с PVC](https://kubernetes.io/docs/concepts/storage/persistent-volumes/).

## Откуда появляется PV

Есть два способа предоставить хранилище. При **статическом предоставлении** администратор подготавливает storage и заранее создаёт PV, а Kubernetes связывает его с подходящим PVC. При **динамическом предоставлении** запрос PVC обрабатывает provisioner выбранного StorageClass: создаёт хранилище и представляющий его PV.

```text
статически:  подготовленное хранилище → PV ← подходящий PVC
динамически: PVC → StorageClass → provisioner → хранилище + PV → PVC Bound
```

Например, PV для уже подготовленного NFS-каталога может выглядеть так. Адрес `192.0.2.10` учебный: для применения нужен настоящий доступный NFS-сервер с экспортированным каталогом и поддержкой NFS на узлах.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: training-data
spec:
  capacity:
    storage: 2Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: ""
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 192.0.2.10
    path: /exports/database
```

В PV указан источник хранилища, а namespace отсутствует. Для такого варианта в создаваемом PVC нужно явно задать `storageClassName: ""`, чтобы запрашивать PV без класса; объём и режим доступа тоже должны подходить. Этот пример — альтернатива динамическому предоставлению, а не дополнительный обязательный объект к `storage-demo.yaml`.

При динамическом предоставлении класс выбирают через `spec.storageClassName` PVC. Например, `storageClassName: standard` означает использовать класс с именем `standard`, если он существует; такое имя не является универсальным для всех кластеров.

| Значение в PVC | Поведение |
|---|---|
| `storageClassName` не задан | Может быть назначен StorageClass по умолчанию |
| `storageClassName: standard` | Запрашивается именно класс `standard` |
| `storageClassName: ""` | Запрашивается PV без класса; динамическое предоставление через класс по умолчанию отключено |

StorageClass — описание способа предоставления, а provisioner — компонент, который выполняет работу. Создание PVC не устанавливает provisioner и не гарантирует появления диска: запрос может остаться `Pending`. Посмотри доступные классы через `kubectl get storageclass` и их настройки через `kubectl describe storageclass CLASS`; механизм описан в [документации StorageClass](https://kubernetes.io/docs/concepts/storage/storage-classes/).

## Режим доступа: Node и Pod — разные ограничения

`ReadWriteOnce` означает чтение и запись с одного Node, а не использование строго одним Pod. Несколько Pod на этом узле могут подключить тот же PVC; если нужен доступ только одному Pod во всём кластере, для совместимого CSI-хранилища существует `ReadWriteOncePod`.

| Режим | Сокращение в выводе | Требуемый доступ |
|---|---|---|
| `ReadWriteOnce` | RWO | Чтение и запись с одного Node |
| `ReadOnlyMany` | ROX | Чтение с нескольких Node |
| `ReadWriteMany` | RWX | Чтение и запись с нескольких Node |
| `ReadWriteOncePod` | RWOP | Использование одним Pod во всём кластере |

Поддержка режима зависит от драйвера и системы хранения; запись `ReadWriteMany` в PVC не добавляет эту возможность обычному диску. `ReadWriteOncePod` поддерживается для CSI volumes при совместимых компонентах драйвера. CSI — интерфейс подключения систем хранения к Kubernetes.

**Режим доступа не решает задачу согласованной записи приложения.** Даже при RWX несколько процессов базы данных не могут без специальной поддержки безопасно работать с одной общей папкой. Кроме того, access modes используются при подборе PV и не заменяют настройку подключения `readOnly: true`, когда контейнеру нужен доступ только для чтения.

## Удаление Pod, PVC и данных

Удаление Pod из примера оставляет PVC `database-data` и связанный PV. Новый Pod может подключить тот же claim и увидеть ранее записанные файлы. StatefulSet для этого не требуется: PVC доступен и обычному Pod, и Pod Deployment; отдельная задача устойчивой идентичности реплик разобрана в [записи 14](14_statefulset_headless_service.md).

| Событие | Что происходит с хранилищем |
|---|---|
| Kubelet перезапустил контейнер в существующем Pod | Подключённый PVC и данные остаются прежними |
| Pod удалён и создан заново с тем же PVC | Замена использует существующий PV, если его можно подключить |
| PVC удалён | Дальнейшая судьба PV и storage определяется политикой освобождения |

Поле **`persistentVolumeReclaimPolicy` у PV** задаёт, что делать с освобождённым томом. У динамически созданного PV политика берётся из `reclaimPolicy` StorageClass; если в классе она не задана, используется `Delete`.

| Политика PV | После удаления PVC |
|---|---|
| `Retain` | PV и данные сохраняются; для повторного использования нужны действия администратора |
| `Delete` | Для поддерживающего это хранилища удаляются PV и соответствующий ресурс системы хранения |

При `Retain` PV обычно переходит из `Bound` в `Released`: прежний запрос удалён, но данные остались. `Released` не равен `Available` — том не становится автоматически свободным для нового PVC. См. [политику освобождения PV](https://kubernetes.io/docs/tasks/administer-cluster/change-pv-reclaim-policy/).

Сохранение данных после замены Pod также не означает доступность с любого узла: локальный том привязан к Node, а облачный диск может быть ограничен зоной. Постоянное хранилище не заменяет резервное копирование: повреждение или удаление данных самим приложением сохраняется на том же volume.

## Основные команды и проверка сохранения файла

```bash
# Проверить классы и применить PVC вместе с Pod
kubectl get storageclass
kubectl apply -f storage-demo.yaml
kubectl wait --for=condition=Ready pod/storage-demo -n study --timeout=60s

# Увидеть связь запроса с предоставленным томом
kubectl get pvc -n study -o wide
kubectl get pv

# Записать учебный файл в подключённое хранилище
kubectl exec storage-demo -n study -- sh -c 'echo saved > /data/marker'

# Заменить только Pod, оставив PVC
kubectl delete pod storage-demo -n study
kubectl apply -f storage-demo.yaml
kubectl wait --for=condition=Ready pod/storage-demo -n study --timeout=60s
kubectl exec storage-demo -n study -- cat /data/marker
# Ожидаем: saved

# Исследовать запрос, предоставленный том и ошибки подключения
kubectl describe pvc database-data -n study
kubectl describe pv PV_NAME
kubectl describe pod storage-demo -n study
```

Здесь Pod создан напрямую, поэтому после удаления его никто не восстанавливает автоматически: замену создаёт повторный `apply`. PVC с тем же именем остаётся существующим объектом, а файл `marker` проверяет, что замена получила прежние данные. `PV_NAME` возьми из колонки `VOLUME` у PVC; PV исследуется без `-n`.

## Если хранилище не подключается

Как в записи 3, начинай с состояния объектов и Events. Цепочка проверки: Pod → нужный PVC → связанный PV → подключение volume → файлы по `mountPath`; к логам приложения переходи, когда контейнер уже получил возможность запуститься.

| Наблюдение | Что проверить |
|---|---|
| PVC не существует | `claimName`, namespace и применение манифеста PVC |
| PVC `Pending` | Есть ли подходящий PV или рабочий provisioner; совпадают ли класс, объём и access modes |
| В Events PVC ожидание первого потребителя | Не использует ли класс `volumeBindingMode: WaitForFirstConsumer` |
| PVC `Bound`, но Pod не запускается | Events Pod: размещение, ограничения узла или зоны, ошибки attach и mount |
| Контейнер запущен, но файлов нет или запись запрещена | Верный ли `mountPath`, использует ли приложение эту папку, подходят ли права и режим чтения |

При `WaitForFirstConsumer` связывание или создание тома откладывается до появления использующего PVC Pod и выбора подходящего размещения. Поэтому `Pending` у ещё не используемого PVC может быть ожидаемым состоянием: не нужно ждать его `Bound` прежде, чем создать Pod. Эта задержка помогает согласовать расположение хранилища с ограничениями запуска приложения.

`Bound` подтверждает связь PVC с PV, но не готовность приложения и не успешное монтирование на выбранном Node. Например, диск ещё может быть подключён к прежнему узлу или у нового узла может не быть доступа к системе хранения. Причину различай по Events PVC и Pod, а не только по колонке STATUS.

## Проверь себя

**1. Чем отличаются PVC и PV? Где находятся сами данные и какие объекты принадлежат namespace?**

<details>
<summary>Показать ответ</summary>

PVC — запрос приложения, PV — ресурс, представляющий предоставленное хранилище. Данные находятся в системе хранения, а не в этих двух объектах или etcd. Pod и PVC принадлежат namespace; PV и StorageClass — ресурсы кластера.

</details>

**2. Создали PVC `database-data`. Получит ли контейнер папку `/data` автоматически?**

<details>
<summary>Показать ответ</summary>

Нет. В Pod нужно объявить volume с `claimName: database-data`, а в контейнере подключить этот volume через `volumeMounts` с `mountPath: /data`. Приложение должно писать именно в подключённую папку.

</details>

**3. В PVC не указан `storageClassName`. Значит ли это то же самое, что `storageClassName: ""`?**

<details>
<summary>Показать ответ</summary>

Нет. При отсутствии поля может быть назначен класс по умолчанию. Явная пустая строка запрашивает PV без класса и отключает динамическое предоставление через класс по умолчанию.

</details>

**4. PVC имеет `ReadWriteOnce`. Обязательно ли он доступен только одному Pod?**

<details>
<summary>Показать ответ</summary>

Нет. Ограничение относится к одному Node; на нём несколько Pod могут использовать тот же PVC. Для ограничения одним Pod существует ReadWriteOncePod при поддержке CSI-хранилищем.

</details>

**5. Pod Deployment подключает отдельный PVC. Нужно ли заменить Deployment на StatefulSet, чтобы сохранить файл при замене Pod?**

<details>
<summary>Показать ответ</summary>

Нет. Замена Pod Deployment может подключить тот же сохранившийся PVC и получить прежний файл. Приложение должно писать в подключённый том, а хранилище должно допускать подключение на выбранном узле. StatefulSet нужен для управления индивидуальными репликами, а не для самого сохранения данных.

</details>

**6. Новый PVC `Pending`, а в Events написано об ожидании первого потребителя. Нужно ли дождаться `Bound` перед созданием Pod?**

<details>
<summary>Показать ответ</summary>

Нет. При WaitForFirstConsumer нужен использующий claim Pod, чтобы согласовать размещение и хранилище. Создай Pod и затем проверь Events обоих объектов; сам Pending здесь ещё не доказывает ошибку.

</details>

**7. Pod удалён, PVC остался. А затем удалили и PVC. Одинаковы ли последствия для данных?**

<details>
<summary>Показать ответ</summary>

Нет. Удаление Pod само по себе сохраняет отдельный PVC и его storage. После удаления PVC действует политика PV: Retain оставляет том и данные для действий администратора, Delete у поддерживаемого хранилища удаляет PV и соответствующий storage. Состояние Released при Retain не означает автоматическую доступность новому claim.

</details>
