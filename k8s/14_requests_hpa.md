# 14. Requests, limits и HPA: ресурсы экземпляра и количество реплик

## Какую проблему решаем

В [записи 5](05_scaling.md) мы вручную меняли количество Pod через `replicas` или `kubectl scale`. При меняющейся нагрузке приложению нужны два отдельных решения: сколько CPU и памяти требуется одному экземпляру и сколько таких экземпляров должно работать сейчас.

**Requests и limits описывают ресурсы контейнера, а HorizontalPodAutoscaler (HPA) автоматически меняет требуемое количество реплик по метрикам.** Настройки, фактическое потребление и решение о масштабировании относятся к разным слоям. Эти слои выражены числами CPU, памяти и Pod, но все-таки различны.

| Понятие | Главный вопрос |
|---|---|
| `requests` | Сколько ресурсов учитывать как потребность контейнера? |
| `limits` | Какие ограничения потребления задать контейнеру? |
| Метрики | Сколько ресурсов используется сейчас? |
| HPA | Сколько экземпляров требуется при таком потреблении? |

## Requests и limits контейнера

Ресурсы задают в `resources` нужного контейнера. В Deployment этот раздел находится внутри `spec.template.spec.containers[]`, поэтому изменение таких настроек меняет шаблон и запускает обновление из записи 6.

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

**Request — потребность, которую учитывает Scheduler при размещении, а не потолок фактического потребления.** Контейнер из примера может использовать больше `100m` CPU и `128Mi` памяти, если ресурсы доступны, с учётом заданных limits. CPU request также влияет на распределение процессорного времени между контейнерами при конкуренции.

| Поле | Значение в примере | Как используется |
|---|---|---|
| `requests.cpu` | `100m` | При размещении требуется учесть 0.1 CPU |
| `requests.memory` | `128Mi` | При размещении требуется учесть 128 MiB памяти |
| `limits.cpu` | `500m` | Ограничивает доступное процессорное время величиной 0.5 CPU |
| `limits.memory` | `256Mi` | Задаёт ограничение памяти; при его превышении возможно завершение из-за OOM |

При достижении CPU limit применяется **throttling**: выполнение ограничивается по процессорному времени, из-за чего приложение может отвечать медленнее. Это само по себе не означает завершения контейнера. Ограничение памяти действует иначе: при превышении возможен OOM kill, а в состоянии завершения контейнера можно увидеть `OOMKilled`.

В Pod Deployment после завершения контейнера kubelet запускает его снова благодаря `restartPolicy: Always`. Это перезапуск внутри того же Pod, знакомый по записи 9; HPA не является механизмом перезапуска.

Request одного ресурса не должен превышать его limit. Если задан только limit и при принятии объекта не назначен другой request, Kubernetes использует значение limit как request для этого ресурса. Поэтому при диагностике смотри принятую конфигурацию Pod, а не только исходный файл: в namespace могут действовать настройки значений по умолчанию.

## Единицы CPU и памяти

CPU задают целыми или дробными единицами либо миллиядрами: `1000m` равно `1` CPU. Например, request `250m` и limit `1000m` означают потребность в 0.25 CPU при размещении и возможность использовать процессорное время до 1 CPU.

Суффикс `m` у CPU означает тысячную долю CPU, а `Mi` и `Gi` у памяти — двоичные единицы размера. Десятичные `M` и `G` тоже допустимы, но отличаются от `Mi` и `Gi`; для памяти в наших примерах используются последние. Количество CPU описывает ресурс вычисления, а не обязательное закрепление контейнера за конкретным физическим ядром.

## Как requests влияют на размещение

Scheduler проверяет, помещается ли потребность нового Pod в доступный для Pod бюджет Node — `allocatable`, с учётом уже размещённых requests. Этот бюджет может быть меньше общей мощности узла, потому что часть ресурсов требуется системе. В простом Pod с несколькими обычными контейнерами их requests складываются; здесь рассматриваем примеры с одним контейнером.

Допустим, для Pod доступно `2 CPU = 2000m`. Если уже размещены Pod A с request `500m` и Pod B с request `1000m`, остаётся бюджет `500m`, и Pod C с request `700m` не помещается.

```text
allocatable: 2000m
занято requests: 500m + 1000m = 1500m
новый request: 700m → сумма 2200m → на этом Node не помещается
```

Низкое текущее потребление не отменяет эту проверку: Pod C может остаться `Pending`, даже если `kubectl top nodes` показывает свободный CPU. Scheduler учитывает заявленные потребности, чтобы размещение не зависело только от момента, когда приложения почти ничего не делают. При нехватке ресурсов причина обычно видна в Events Pod, например `Insufficient cpu` или `Insufficient memory`.

## Настроенные ресурсы и фактическое потребление

`requests` и `limits` находятся в конфигурации API, а `kubectl top pods` и `kubectl top nodes` показывают метрики потребления. Контейнер с request `100m` может сейчас потреблять `20m`, а через минуту — `180m`; его request от этого сам не меняется.

```text
контейнеры на Node → kubelet → Metrics Server → Metrics API
                                                   ├→ kubectl top
                                                   └→ HPA по CPU или памяти
```

Metrics Server обычно собирает показатели с kubelet и предоставляет их через Kubernetes API. Для `top` и нашего HPA нужен работающий поставщик resource metrics; создание HPA само по себе его не устанавливает. Метрики поступают с задержкой, а CPU измеряется за временное окно, поэтому `top` не является мгновенным снимком каждой операции.

## Механизм HPA

HPA периодически получает метрики, сравнивает их с целью и корректирует масштаб целевого ресурса. Для Deployment это означает изменение требуемого количества реплик, после чего обычная цепочка Deployment → ReplicaSet → Pod создаёт или убирает экземпляры. HPA не запускает контейнеры самостоятельно и не меняет их requests или limits.

```text
нагрузка → потребление CPU Pod → метрики → HPA сравнивает с target
                                                ↓
                          replicas Deployment → ReplicaSet → Pod
                                                ↓
                          нагрузка распределяется между репликами
```

Это цикл обратной связи: новые экземпляры могут принять часть работы, затем HPA снова оценивает потребление. Он задаёт количество в пределах `minReplicas` и `maxReplicas`; например, диапазон `1..4` ограничивает желаемое число реплик четырьмя. Во время rollout дополнительные или завершающиеся Pod могут временно увеличить число видимых объектов — граница HPA не заменяет стратегию обновления Deployment.

Здесь рассматриваем CPU, но HPA также поддерживает память и другие метрики при наличии подходящего поставщика. Он применим к ресурсам с интерфейсом масштабирования, в том числе Deployment и StatefulSet. DaemonSet из записи 11 не имеет заданного числа реплик: его количество Pod определяется подходящими узлами.

## CPU utilization: процент относительно request

**В HPA с CPU-целью типа `Utilization` процент считается от CPU request, а не от limit и не от мощности Node.** Для контейнера с request `500m` и потреблением `350m` утилизация равна `350 / 500 × 100% = 70%`. В наших примерах у всех реплик один контейнер с одинаковым request, поэтому HPA оценивает среднее потребление реплик относительно этого значения.

```text
request: 500m, потребление: 350m → utilization: 70%
request: 100m, цель: 30%         → ориентир среднего потребления: 30m на Pod
```

Утилизация может быть выше 100%: например, при request `100m` и потреблении `180m` получится 180%, если limit допускает такую работу. Если при том же потреблении увеличить request до `200m`, процент станет 90%. Поэтому изменение request влияет сразу и на размещение, и на то, какую загрузку увидит HPA.

Для CPU-метрики типа `Resource` нужный CPU request должен быть задан у учитываемых контейнеров, включая дополнительные контейнеры Pod. Без него процент может оказаться неопределённым, и HPA не сможет использовать эту метрику для масштабирования. Наличие CPU limit само по себе не является формулой процента: проверь фактический request, который принят API.

## Пример Deployment, Service и HPA

Сначала создай приложение с ресурсами и внутренним Service. Сохрани эти два объекта как `cpu-demo.yaml`; образ `hpa-example` из исходника выполняет вычисления при HTTP-запросах и подходит для учебной проверки роста CPU.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cpu-demo
  namespace: study
spec:
  selector:
    matchLabels:
      app: cpu-demo
  template:
    metadata:
      labels:
        app: cpu-demo
    spec:
      containers:
        - name: app
          image: registry.k8s.io/hpa-example:latest
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 100m
              memory: 32Mi
            limits:
              cpu: 200m
              memory: 64Mi
---
apiVersion: v1
kind: Service
metadata:
  name: cpu-demo
  namespace: study
spec:
  selector:
    app: cpu-demo
  ports:
    - port: 80
      targetPort: http
```

Размеры ресурсов сохранены из исходного учебного примера. Service нужен клиенту для создания HTTP-нагрузки, а HPA выбирает Pod через целевой Deployment, независимо от Service. В этом новом Deployment `replicas` не задано: по умолчанию создаётся одна реплика, затем количеством управляет HPA.

Сам HPA сохрани отдельно как `cpu-demo-hpa.yaml`. Используем `autoscaling/v2`, чтобы явно записать ресурс, тип цели и требуемый процент.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cpu-demo
  namespace: study
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: cpu-demo
  minReplicas: 1
  maxReplicas: 4
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 30
```

| Поле HPA | Что задаёт |
|---|---|
| `scaleTargetRef` | Какой ресурс масштабировать в namespace HPA |
| `minReplicas`, `maxReplicas` | Нижнюю и верхнюю границы желаемого количества реплик |
| `metrics[].type: Resource` | Использование ресурсной метрики Pod |
| `resource.name: cpu` | Масштабирование по CPU |
| `target.type: Utilization` | Цель как процент от requests |
| `averageUtilization: 30` | Целевую среднюю утилизацию 30% |

Можн создать через команду `kubectl autoscale deployment cpu-demo -n study --cpu=30% --min=1 --max=4`. В старых версиях kubectl используется `--cpu-percent=30`.

## Как читать состояние и решение о масштабе

После получения метрик `kubectl get hpa cpu-demo -n study` может показать такой промежуточный результат. Колонка `TARGETS` сопоставляет текущее значение с целью; это наблюдение, а не обещание, что желаемое количество уже достигнуто.

```text
NAME       REFERENCE             TARGETS   MINPODS   MAXPODS   REPLICAS
cpu-demo   Deployment/cpu-demo   55%/30%   1         4         2
```

Здесь средняя утилизация — 55% от request при цели 30%, а HPA пока наблюдает две реплики. В базовом расчёте требуемое число равно текущему числу, умноженному на отношение метрики к цели, с округлением вверх:

```text
desiredReplicas = ceil(currentReplicas × currentUtilization / targetUtilization)
ceil(2 × 55 / 30) = ceil(3.67) = 4
```

Если результат выходит за диапазон, применяются границы HPA. Но формула — основа решения, а не точное предсказание любого следующего шага: контроллер также учитывает готовность Pod, недостающие метрики, допустимые отклонения и правила изменения масштаба. Поэтому один вывод `55%/30%` недостаточен для вывода, что четыре готовых Pod должны появиться немедленно.

При снижении нагрузки HPA может некоторое время сохранять прежний масштаб, чтобы не создавать и не удалять Pod при каждом колебании. По умолчанию для уменьшения используется окно стабилизации 300 секунд: учитываются рекомендации за это окно, а не только последняя низкая метрика. Это не обещание уменьшить число ровно через пять минут после остановки клиента.

## Основные команды и проверка под нагрузкой

```bash
# Проверить доступность ресурсных метрик
kubectl top nodes
kubectl top pods -n study

# Применить приложение, дождаться запуска и создать HPA
kubectl apply -f cpu-demo.yaml
kubectl rollout status deployment/cpu-demo -n study --timeout=60s
kubectl apply -f cpu-demo-hpa.yaml

# Наблюдать потребление, состояние HPA и фактические Pod
kubectl top pods -n study -l app=cpu-demo --containers
kubectl get hpa cpu-demo -n study
kubectl describe hpa cpu-demo -n study
kubectl get pods -n study -l app=cpu-demo -o wide

# Сравнить метрики с принятой конфигурацией контейнера
kubectl get pod POD -n study -o yaml
kubectl describe pod POD -n study

# Запустить HTTP-нагрузку в отдельном терминале
kubectl run load-generator -n study --image=busybox:1.36 \
  --restart=Never --rm -it -- sh -c \
  'while sleep 0.01; do wget -q -O- http://cpu-demo; done'

# В другом терминале наблюдать решение HPA
kubectl get hpa cpu-demo -n study -w
```

`--containers` показывает метрики отдельных контейнеров, `POD` замени на имя экземпляра приложения. Нагрузка идёт через Service внутри кластера; останови её через Ctrl+C в терминале клиента. Если клиентский Pod остался, удали его через `kubectl delete pod load-generator -n study`, чтобы прекратить запросы; Ctrl+C в окне `get -w` останавливает только наблюдение.

После остановки клиента сравни метрики, состояние HPA и количество Pod ещё раз. Масштаб может измениться с задержкой, а итоговое число зависит от фактической нагрузки и состояния кластера. Такой эксперимент описан в [учебном примере HPA](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/); установка Metrics Server относится к подготовке учебного кластера.

## Кто управляет replicas

При ручном масштабировании из записи 5 число задавал пользователь через файл или `scale`. При включённом HPA это поле регулярно меняет контроллер: ручной `scale` может быть скорректирован следующим решением HPA, а повторный `apply` с явно записанным `replicas: 1` может вернуть одну реплику и начать спорить с автомасштабированием.

Поэтому в нашем примере нового Deployment фиксированное `spec.replicas` отсутствует в YAML с самого начала. Настройки ресурсов остаются в шаблоне Deployment, а границы и цель масштабирования — в HPA. Сам HPA меняет объект в API и не переписывает файлы на диске.

## Три уровня масштабирования

HPA, VPA и масштабирование узлов отвечают на разные вопросы. Их действия могут дополнять друг друга, но создание HPA не включает автоматически остальные механизмы.

| Механизм | Что меняет | Какая задача решается |
|---|---|---|
| HPA | Требуемое количество реплик приложения | Добавить или убрать экземпляры |
| VPA — VerticalPodAutoscaler | Рекомендации и, в зависимости от режима, requests контейнеров | Подобрать ресурсы одного экземпляра |
| Масштабирование Node | Количество или состав узлов кластера | Предоставить место для размещения Pod |

## Если автомасштабирование не даёт ожидаемый результат

Как в записи 3, выбирай диагностику по нарушенному этапу: метрики → расчёт HPA → желаемые replicas → создание и размещение Pod → готовность приложения. Наличие HPA не гарантирует доступность метрик, возможность запуска дополнительных экземпляров или правильность выбранного сигнала нагрузки.

| Наблюдение | Что проверить |
|---|---|
| `top` не получает метрики, у HPA `<unknown>` | Доступность Metrics API и работу Metrics Server; сразу после запуска возможна задержка появления метрик |
| `top` работает, но HPA не рассчитывает CPU utilization | CPU requests всех учитываемых контейнеров, `scaleTargetRef`, Conditions и Events HPA |
| HPA требует больше реплик, новые Pod `Pending` | Events Pod: хватает ли allocatable ресурсов и подходят ли узлы |
| Растёт `RESTARTS`, видно `OOMKilled` | Потребление памяти, memory limit и поведение приложения; добавление реплик не исправляет любую нехватку памяти |
| Приложение тормозит около CPU limit | Возможный throttling; одно значение `top` само по себе его не доказывает |
| Нагрузка высокая, достигнут `maxReplicas` | Верхнюю границу и способность приложения распределять работу между экземплярами |
| Нагрузка упала, количество не уменьшается сразу | Нижнюю границу, окно стабилизации и правила масштабирования |

У HPA полезны Conditions:

- `AbleToScale` — возможность работать с масштабом цели
- `ScalingActive` — возможность рассчитывать его по метрикам
- `ScalingLimited` — ограничение рассчитанного масштаба

Например, `ScalingLimited=True` может означать достижение границы, а не поломку контроллера. 

## Проверь себя

**1. На Node почти нет фактической нагрузки, но requests уже заняли весь доступный бюджет. Почему новый Pod может остаться Pending?**

<details>
<summary>Показать ответ</summary>

Scheduler проверяет заявленные requests относительно allocatable и уже размещённых потребностей. Низкое потребление в top не отменяет эту проверку: приложению может понадобиться запрошенный ресурс позже.

</details>

**2. Контейнер потребляет больше request. Обязательно ли он будет остановлен? Что различается у CPU limit и memory limit?**

<details>
<summary>Показать ответ</summary>

Нет: request не является потолком, и контейнер может использовать больше при доступных ресурсах и подходящих limits. CPU limit ограничивает процессорное время через throttling; превышение memory limit может привести к OOMKilled и дальнейшему перезапуску по restartPolicy.

</details>

**3. CPU request равен 500m, потребление — 350m, цель HPA — 70%. Относительно чего считается процент?**

<details>
<summary>Показать ответ</summary>

Относительно request: 350 / 500 × 100% = 70%. Это не доля CPU Node и не доля CPU limit. Для одинаковых реплик среднее значение 70% соответствует цели.

</details>

**4. Потребление осталось 180m, а request изменили со 100m на 200m. Что произойдёт с CPU utilization для HPA?**

<details>
<summary>Показать ответ</summary>

Она изменится со 180% на 90%, хотя реальное потребление осталось прежним. Request задаёт базу процента и также влияет на размещение; значение выше 100% допустимо, если контейнер использует больше request.

</details>

**5. Есть две готовые реплики с полными метриками, текущая утилизация 55%, цель 30%, диапазон 1..4. Каков базовый расчёт HPA?**

<details>
<summary>Показать ответ</summary>

ceil(2 × 55 / 30) = 4, что укладывается в диапазон. Это расчёт желаемого масштаба, а не гарантия немедленного появления четырёх готовых Pod: действуют правила HPA и ограничения запуска.

</details>

**6. У HPA показано `<unknown>/30%`. Значит ли это, что CPU не используется или метрика равна нулю?**

<details>
<summary>Показать ответ</summary>

Нет. Текущее значение не удалось получить или рассчитать. Проверь Metrics API, метрики Pod и CPU requests учитываемых контейнеров; причину уточняй в Conditions и Events HPA.

</details>

**7. HPA добавил требуемые реплики, но новые Pod Pending из-за нехватки CPU. Увеличил ли HPA resources контейнеров или число узлов?**

<details>
<summary>Показать ответ</summary>

Нет. HPA меняет только желаемое количество экземпляров. Ресурсы экземпляра относятся к requests/limits и VPA, доступная инфраструктура — к масштабированию Node, а размещение выполняет Scheduler.

</details>

**8. HPA поддерживает четыре реплики, но в старом YAML осталось `replicas: 1`. Что может сделать повторный apply?**

<details>
<summary>Показать ответ</summary>

Вернуть желаемое количество к одной реплике, после чего HPA может снова изменить его по метрикам. Чтобы конфигурации не спорили, управление количеством передают HPA, сохраняя его границы и цель в отдельном объекте; сам HPA локальный YAML не исправляет.

</details>
