# Kubernetes: конспекты для понимания и повторения

Главная идея Kubernetes: **ты задаёшь желаемое состояние, а контроллеры постоянно пытаются привести фактическое состояние к нему**. Этот процесс называется reconciliation — согласование.

## Как работать с конспектами

1. Прочитай объяснение и проговори механизм своими словами.
2. Закрой текст и ответь на вопросы в конце темы. Сначала предскажи результат, затем объясни причину.
3. Открой ответы и проверь себя. Если ошибся, вернись к соответствующему различию.
4. Когда есть учебный кластер, проверь прогноз командами. Ресурсы namespace меняй в своём учебном namespace; ресурсы уровня кластера, например метки Node, — в своём учебном кластере.

Не нужно заучивать весь синтаксис. Нужно понимать, **какой объект ты меняешь, какое поле меняется и что после этого делает Kubernetes**. Редкие флаги ищи через `--help`.

## Общая модель

```text
YAML → kubectl apply → API Server → желаемое состояние в кластере
                                         │
                                  контроллеры согласуют
                                         ↓
Deployment → ReplicaSet → Pod → контейнеры
DaemonSet               → Pod → контейнеры
StatefulSet             → Pod → контейнеры
Job                     → Pod → контейнеры
CronJob → Job           → Pod → контейнеры

Клиент → Service → подходящие готовые backend Pod
Pod → использует PVC → связанный PV → хранилище с данными
```

Scheduler выбирает узел для нового Pod. Kubelet на выбранном узле обеспечивает запуск контейнеров. EndpointSlice отражает адреса backend Service и их готовность.

Состояние оценивают относительно цели: для приложения важна готовность обслуживать запросы, для Job — успешное завершение, для DaemonSet — наличие агента на каждом подходящем узле. StatefulSet сохраняет идентичность экземпляров и их связь с хранилищем, CronJob добавляет расписание создания Job. Поэтому сначала определи, кто управляет Pod и какого результата от него ждёт.

## Три состояния, которые нельзя смешивать

| Где | Что это |
|---|---|
| YAML на диске | Сохранённая конфигурация, которую ты собираешься применить |
| `spec` объекта в API | Желаемое состояние, уже принятое кластером |
| `status` объекта | Наблюдаемое состояние, о котором сообщает Kubernetes |

Kubernetes не перечитывает твой локальный YAML сам по себе. `scale` и `rollout undo` меняют объект в API, но не файл. Следующий `apply` может снова применить старую конфигурацию из файла.

## Как читать команды

```bash
kubectl rollout status deployment/web -n study --timeout=60s
```

| Часть | Значение |
|---|---|
| `kubectl` | Клиент Kubernetes |
| `rollout` | Группа команд управления развёртыванием |
| `status` | Действие: наблюдать за состоянием развёртывания |
| `deployment/web` | Тип ресурса и его имя |
| `-n study` | Namespace ресурса |
| `--timeout=60s` | Максимальное время ожидания этой команды |

В примерах используется приложение `web` в namespace `study`. Имена файлов в командах — примеры манифестов, их нужно создать или заменить на свои. Эти конспекты сами по себе не являются манифестами.

```bash
kubectl config current-context
kubectl create namespace study
kubectl rollout status --help
```

Создание namespace нужно выполнить один раз, если он ещё не существует.
