# Kubernetes: конспекты для понимания и повторения

Главная идея Kubernetes: **надо задать желаемое состояние, а контроллеры будут постоянно пытаться привести фактическое состояние к нему**. Этот процесс называется reconciliation — согласование.

`notes/` — конспекты, `labs/` — отдельные YAML для небольших практик, `projects/` — проекты с несколькими файлами: приложение с PostgreSQL и Helm chart.

## Как работать с конспектами

1. Прочитай объяснение и проговори механизм своими словами.
2. Закрой текст и ответь на вопросы в конце темы. Сначала предскажи результат, затем объясни причину.
3. Открой ответы и проверь себя. Если ошибся, вернись к соответствующему различию.
4. Когда есть учебный кластер, проверь прогноз командами. Ресурсы namespace меняй в своём учебном namespace. Ресурсы уровня кластера, например метки Node, — в своём учебном кластере.

Главное — понимать, **какой объект ты меняешь, какое поле меняется и что после этого делает Kubernetes**. Редкие флаги ищи через `--help`.

## Общая модель

```text
YAML → kubectl apply → API Server → желаемое состояние в кластере
                                         │
                                  контроллеры согласуют
                                         ↓
Deployment → ReplicaSet → Pod → контейнеры
DaemonSet               → Pod → контейнеры
StatefulSet             → Pod → контейнеры
Job                     → Pod → контейнеры
CronJob → Job           → Pod → контейнеры

Клиент → Service → подходящие готовые backend Pod
Внешний HTTP-клиент → прокси Gateway → backend по правилам HTTPRoute
Pod → использует PVC → связанный PV → хранилище с данными
```

Scheduler выбирает узел для нового Pod. Kubelet на выбранном узле обеспечивает запуск контейнеров. EndpointSlice отражает адреса backend Service и их готовность.

Состояние оценивают относительно цели: для приложения важна готовность обслуживать запросы, для Job — успешное завершение, для DaemonSet — наличие агента на каждом подходящем узле. StatefulSet сохраняет идентичность экземпляров и их связь с хранилищем, CronJob добавляет расписание создания Job.

## Файл, spec и status

| Где | Что это |
|---|---|
| YAML на диске | Сохранённая конфигурация, которую ты собираешься применить |
| `spec` объекта в API | Желаемое состояние, уже принятое кластером |
| `status` объекта | Наблюдаемое состояние, о котором сообщает Kubernetes |

Kubernetes использует конфигурацию, переданную через API. `scale` и `rollout undo` меняют объект в API. Файл на диске остаётся прежним. Следующий `apply` может снова применить старую конфигурацию из файла.

## Как читать команды

```bash
kubectl rollout status deployment/web -n study --timeout=60s
```

| Часть | Значение |
|---|---|
| `kubectl` | Клиент Kubernetes |
| `rollout` | Группа команд управления развёртыванием |
| `status` | Действие: наблюдать за состоянием развёртывания |
| `deployment/web` | Тип ресурса и его имя |
| `-n study` | Namespace ресурса |
| `--timeout=60s` | Максимальное время ожидания этой команды |

Примеры используют namespace `study`. Имя файла указано в начале полного YAML-манифеста. Фрагменты показывают изменения в отдельных частях конфигурации.

```bash
kubectl config current-context
kubectl create namespace study
kubectl rollout status --help
```

Создание namespace нужно выполнить один раз, если он ещё не существует.

## Сокращения ресурсов в kubectl

В командах можно использовать короткое имя типа ресурса. Например, `kubectl get rs` означает то же, что `kubectl get replicasets`.

| Ресурс | Сокращение |
|---|---|
| Pod | `po` |
| Deployment | `deploy` |
| ReplicaSet | `rs` |
| Service | `svc` |
| Namespace | `ns` |
| ConfigMap | `cm` |
| ServiceAccount | `sa` |
| DaemonSet | `ds` |
| StatefulSet | `sts` |
| CronJob | `cj` |
| Ingress | `ing` |
| NetworkPolicy | `netpol` |
| PersistentVolume | `pv` |
| PersistentVolumeClaim | `pvc` |
| HorizontalPodAutoscaler | `hpa` |

```bash
# Несколько типов ресурсов в одной команде
kubectl get deploy,rs,po,svc -n study

# Все доступные типы ресурсов и их сокращения в колонке SHORTNAMES
kubectl api-resources
```
