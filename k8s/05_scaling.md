# 5. Масштабирование: изменить количество экземпляров

## Какую проблему решает масштабирование

Приложению может понадобиться больше или меньше одновременно работающих экземпляров. **Горизонтальное масштабирование меняет количество Pod**, а не количество CPU или памяти одного Pod.

В этих занятиях масштабирование ручное. Автоматическое масштабирование — отдельная тема.

## Механизм

```text
spec.replicas: 2 → 4
         ↓
Deployment меняет требуемое количество реплик ReplicaSet
         ↓
ReplicaSet создаёт недостающие Pod
         ↓
новые Pod запускаются и становятся готовыми
         ↓
обновляется набор backend Service
```

При уменьшении количества лишние Pod завершаются. Service сохраняет своё имя и IP, а EndpointSlice отражает изменившийся набор backend.

Если шаблон не меняется и активного обновления нет, масштабируется тот же ReplicaSet. Новая ревизия Deployment не создаётся. Во время незавершённого rollout масштабирование может затронуть несколько активных ReplicaSet.

## Два способа изменить количество

**Декларативно:** изменить файл и применить его.

```yaml
spec:
  replicas: 4
```

```bash
kubectl diff -f web.yaml
kubectl apply -f web.yaml
```

**Императивно:** изменить объект в работающем кластере.

```bash
kubectl scale deployment/web -n study --replicas=4
```

Оба способа меняют `spec.replicas` объекта в API. Разница в том, отражено ли изменение в сохранённом файле.

## Файл, желаемое состояние и реальность

Допустим, в YAML записано `replicas: 4`, затем ты выполнил `scale --replicas=2`.

| Место | Значение |
|---|---|
| YAML на диске | 4 |
| `spec.replicas` в API | 2 |
| Готовые Pod | Сначала может быть другое число, затем ожидаются 2 |

Для контроллера действующее желаемое состояние сейчас — **2**, потому что оно находится в API. Файл на диске сам по себе не влияет на кластер.

Следующий `apply` файла, явно задающего 4 реплики, может вернуть требование к четырём. Если хочешь сохранить две — исправь YAML.

## Основные команды

```bash
# Изменить количество
kubectl scale deployment/web -n study --replicas=4

# Проверить достижение состояния
kubectl rollout status deployment/web -n study --timeout=60s
kubectl get deployment web -n study
kubectl get pods -n study -l app=web -o wide

# Посмотреть backend и события
kubectl get endpointslices -n study -l kubernetes.io/service-name=web -o yaml
kubectl describe deployment web -n study
```

`--replicas=4` — требуемое число Pod, а не обещание четырёх готовых экземпляров прямо сейчас. Ресурсов узлов может не хватить или контейнеры могут не запуститься.

После масштабирования можно использовать `rollout status` для проверки достижения состояния. Это **не означает**, что масштабирование создало новую ревизию.

## Не путай

| Действие | Что меняется |
|---|---|
| Масштабирование | Количество экземпляров |
| Обновление шаблона | Конфигурация создаваемых экземпляров |
| Пересоздание отдельного Pod | Конкретный экземпляр, при прежнем шаблоне и числе реплик |

Service распределяет соединения между backend, но не гарантирует одинаковое число запросов на каждый Pod. Одно длительное соединение также не обязано переключаться между Pod.

**1. Число реплик выросло с 2 до 4. Нужно ли менять Service?**

**2. Создаст ли изменение только `spec.replicas` новую ревизию Deployment?**

<details>
<summary>Показать ответ</summary>

</details>

**3. В YAML 4 реплики, после `scale` в API 2. Какое число пытаются поддерживать контроллеры?**

<details>
<summary>Показать ответ</summary>

Две, пока желаемое состояние в API не будет изменено снова.

</details>

**4. Почему `spec.replicas: 4` и четыре готовых Pod — разные утверждения?**

<details>
<summary>Показать ответ</summary>

Первое — требование. Второе — достигнутое состояние. Между ними есть запуск, размещение, загрузка образов и возможные ошибки.

</details>
