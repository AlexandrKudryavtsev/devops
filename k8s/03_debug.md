# 3. Диагностика: найти слой, на котором произошла ошибка

## Какую проблему решает диагностика

«Приложение не работает» может означать разные вещи: Pod не разместился, образ не скачался, процесс завершился или приложение не отвечает по сети. Команду выбирают по этапу, на котором возникла проблема.

## Механизм поиска

```text
get: найти проблемный Pod
          ↓
describe + Events: понять состояние и ошибки Kubernetes
          ↓
если контейнер запускался → logs: исследовать приложение
если контейнер работает → exec: проверить его изнутри
          ↓
исправить конфигурацию → apply → проверить результат
```

Это ориентир, а не требование выполнить все команды строго по порядку. Если контейнер падает, логи нужны до исправления, а не только после него.

## Что говорит каждый инструмент

| Команда | Что узнаёшь |
|---|---|
| `get` | Какие объекты есть, их состояние и число готовых контейнеров |
| `describe` | Конфигурацию, состояния контейнеров, Conditions и связанные Events |
| `get events` | Последовательность диагностических событий Kubernetes |
| `logs` | stdout и stderr приложения |
| `exec` | Результат команды внутри работающего контейнера |

Events — не логи приложения и не вечный архив. Logs — не полная история действий Kubernetes.

## Сначала распознай симптом

| Симптом | Что означает | С чего начать |
|---|---|---|
| `Pending` | Pod ещё не перешёл к нормальной работе; причина требует проверки | `describe`, Events, назначен ли Node |
| `ErrImagePull` / `ImagePullBackOff` | Не получается получить образ | Events: имя образа, доступ к registry, сеть |
| `CrashLoopBackOff` | Контейнер повторно падает, между попытками есть задержка | `logs`, `logs --previous`, `describe` |
| `Running`, но не Ready | Pod запущен, но готовность не подтверждена | Conditions, состояния контейнеров, проверки готовности |
| Pod Ready, Service не отвечает | Проблема может быть в сетевом пути или приложении | Selector, EndpointSlice, порты, проверка изнутри |

`Running` — фаза Pod. `ImagePullBackOff` и `CrashLoopBackOff` — причины состояния контейнера, которые `kubectl` может показывать в колонке STATUS. Это не отдельные фазы Pod.

`READY 1/1` означает, что один контейнер из одного готов. Без настроенной readiness probe этот статус не доказывает правильность бизнес-логики приложения.

## Основные команды

```bash
kubectl get pods -n study -l app=web -o wide
kubectl describe pod POD -n study

# События конкретного Pod
kubectl get events -n study \
  --field-selector involvedObject.kind=Pod,involvedObject.name=POD \
  --sort-by='.metadata.creationTimestamp'

# Логи текущего и предыдущего запуска контейнера
kubectl logs POD -n study --tail=50
kubectl logs POD -n study --previous

# Команда внутри работающего контейнера
kubectl exec POD -n study -- nginx -t
```

`--previous` полезен, когда предыдущий экземпляр контейнера уже завершился. Если контейнеров несколько, явно укажи нужный через `-c CONTAINER` для `logs` и `exec`.

В `exec` разделитель `--` отделяет параметры kubectl от выполняемой команды. Команда и её инструменты должны существовать внутри контейнера.

## Что достаточно уметь найти

```bash
# Получить одно поле вместо полного описания
kubectl get pod POD -n study -o jsonpath='{.spec.containers[0].image}'

# Выбрать Pod по фазе
kubectl get pods -n study --field-selector=status.phase=Running
```

JSONPath достаёт поля из результата. `-l` фильтрует по меткам, `--field-selector` — по поддерживаемым полям объекта. Синтаксис сложных выражений можно искать по необходимости.

**1. Pod показывает `ImagePullBackOff`. Почему логи приложения могут ничего не объяснить?**

**2. Контейнер запустился и сразу упал. Можно ли изучить его логи?**

<details>
<summary>Показать ответ</summary>

Да. Смотри `logs`, а после перезапуска — `logs --previous`. Для `exec` требуется работающий контейнер.

</details>

**3. Pod имеет фазу Running. Значит ли это, что он готов обслуживать запросы?**

<details>
<summary>Показать ответ</summary>

Нет. Running и Ready описывают разные стороны состояния; даже Ready не является полной проверкой приложения.

</details>

**4. Что проверяет `exec POD -- wget http://127.0.0.1:80` и чего не проверяет?**

<details>
<summary>Показать ответ</summary>

Проверяет ответ приложения на localhost внутри Pod, если wget есть в контейнере. Не проверяет DNS Service, его selector, ClusterIP или NodePort.

</details>
