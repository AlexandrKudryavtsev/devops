# 6. Rollout: обновление, наблюдение и откат

## Какую проблему решает rollout

Нужно заменить версию приложения, управляя переходом между старыми и новыми экземплярами. **Rollout — процесс развёртывания нового шаблона Pod.** 

`kubectl rollout` — группа команд для управления развёртыванием и наблюдения за ним. Само обновление после изменения манифеста выполняет контроллер Deployment.

## Что запускает обновление

**Изменение `spec.template`**, например `image`, запускает rollout неприостановленного Deployment. **Ревизия** — сохранённая версия шаблона Pod, к которой можно вернуться.

```text
новый Pod template
        ↓
новая ревизия
        ↓
новый ReplicaSet или повторное использование подходящего старого
        ↓
замена набора Pod
```

Для ранее не использовавшегося шаблона обычно создаётся новый ReplicaSet. При возврате к сохранённому шаблону подходящий старый ReplicaSet может использоваться снова.

Deployment создаёт Pod по новому шаблону и удаляет старые. Старые ReplicaSet могут сохраняться с нулём реплик для истории и отката. История ограничена настройками Deployment.

Изменение меток внутри `spec.template` тоже запускает rollout. Изменения вне шаблона решают другие задачи: `replicas` — масштабирование, `strategy` — порядок обновления, `metadata.labels` — метки самого Deployment.

## Как читать команду status

```bash
kubectl rollout status deployment/web -n study --timeout=60s
```

`rollout` — группа, `status` — действие, `deployment/web` — тип и имя ресурса, `-n` — namespace, `--timeout` — ограничение ожидания.

`status` наблюдает за последним развёртыванием и по умолчанию ждёт завершения. Успех означает, что новые реплики доступны и замена старых завершена. Работу самого приложения проверяют отдельно.

```bash
# Показать состояние без ожидания
kubectl rollout status deployment/web -n study --watch=false

# Наблюдать за конкретной ревизией
kubectl rollout status deployment/web -n study --revision=3 --timeout=2m
```

Без `--revision` команда может переключиться на новое развёртывание, начавшееся во время ожидания. `--revision=3` фиксирует выбранную ревизию. Ноль в `--timeout` означает отсутствие ограничения ожидания.

**Тайм-аут завершает ожидание kubectl. Контроллер продолжает обновление. Для отката нужна отдельная команда `undo`.**

## Основные подкоманды

| Подкоманда | Назначение | Главный параметр |
|---|---|---|
| `status` | Наблюдать за развёртыванием | `--timeout`, `--watch`, `--revision` |
| `history` | Посмотреть сохранённые ревизии | `--revision` для деталей одной ревизии |
| `undo` | Вернуть предыдущий или выбранный шаблон | `--to-revision` |
| `restart` | Запустить пересоздание Pod | Можно выбрать Deployment через `-l` |
| `pause` / `resume` | Приостановить и продолжить rollout Deployment | Тип и имя ресурса |

```bash
kubectl rollout history deployment/web -n study
kubectl rollout history deployment/web -n study --revision=2

# Вернуть предыдущую сохранённую ревизию
kubectl rollout undo deployment/web -n study

# Вернуть конкретную сохранённую ревизию
kubectl rollout undo deployment/web -n study --to-revision=2

# Пересоздать Pod, не выбирая новый тег image
kubectl rollout restart deployment/web -n study
```

`undo` и `restart` запускают изменение, но готовность проверяют отдельно через `status`. `undo` возвращает сохранённый шаблон. Его исправность нужно проверить: предыдущая ревизия тоже может содержать ошибку.

Для повторения достаточно свободно понимать `status`, `history` и `undo`. Остальные команды и дополнительные флаги можно находить через `kubectl rollout SUBCOMMAND --help`.

## RollingUpdate: как управлять переходом

```yaml
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0 # Сохранять как минимум 3 доступные реплики
      maxSurge: 1       # Разрешить одну дополнительную реплику
```

Для заданных в YAML трёх реплик переход выглядит так:

```text
OLD OLD OLD
OLD OLD OLD NEW   ← новый Pod создаётся
OLD OLD NEW       ← после его готовности один старый убирается
... → NEW NEW NEW
```

Для дополнительного Pod нужны ресурсы. Завершающиеся Pod тоже могут временно занимать ресурсы, поэтому одновременно видимых Pod может быть больше четырёх.

## Service во время обновления

Service выбирает Pod по меткам, а не по ревизии. Во время rollout среди готовых backend могут одновременно быть старая и новая версии.

Если новый образ не скачивается, старые готовые Pod могут продолжать отвечать. Поэтому ответ Service не доказывает успешное завершение выпуска. Проверяй rollout и образы Pod.

## Откат и файл

Rollback восстанавливает сохранённый Pod template и присваивает ему новый номер ревизии. Остальные поля Deployment и YAML на диске остаются прежними.

Если в файле остался неисправный image, следующий `apply` снова применит его. После восстановления нужно исправить сохранённую конфигурацию.
