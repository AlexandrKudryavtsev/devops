# 13. PV и PVC: как сохранить данные при замене Pod

## Какую проблему решаем

`emptyDir` из [записи 12](12_volumes.md) теряет файлы вместе с Pod. Если приложению нужно сохранить данные, ему подключают отдельное постоянное хранилище. После замены Pod новый экземпляр подключает то же хранилище и продолжает работать с файлами.

Разберём одну цепочку: в кластере настроен способ создания хранилища → приложение запрашивает нужный объём → Kubernetes подбирает или создаёт том → контейнер получает папку для файлов.

## Шаг 1. В кластере настраивают StorageClass и provisioner

Сначала администратор кластера или облачный провайдер настраивает **provisioner — компонент, который умеет создавать хранилище**, например облачные диски. Затем создаёт **StorageClass — объект с настройками создания хранилища**. В нём поле `provisioner` указывает, какой компонент выполнит запрос, а `parameters` содержит настройки для него, например тип диска.

Допустим, в нашем кластере уже есть StorageClass `fast` с работающим provisioner. Дальше будем запрашивать хранилище этого класса. `fast` — имя для примера. В своём кластере выбирают существующий класс.

## Шаг 2. Приложение запрашивает хранилище через PVC

**PersistentVolumeClaim (PVC) — заявка на хранилище.** Её создают отдельным объектом, а затем указывают в Pod.

Допустим, приложению нужно 2 ГиБ с доступом на чтение и запись с одного узла. Создадим заявку `database-data` и выберем класс `fast`:

```yaml
# storage-demo.yaml — PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-data
  namespace: study
spec:
  storageClassName: fast   # Имя StorageClass из шага 1
  accessModes:
    - ReadWriteOnce       # Чтение и запись с одного Node
  resources:
    requests:
      storage: 2Gi        # Нужно не меньше 2 ГиБ
```

**Поле `storageClassName` связывает заявку с классом по имени.** По значению `fast` Kubernetes понимает, какое хранилище искать и к какому provisioner обратиться, если понадобится создать новое.

## Шаг 3. Kubernetes подбирает или создаёт PV

**PersistentVolume (PV) — объект Kubernetes, который описывает конкретное хранилище:** где оно находится, какого оно объёма и какой доступ поддерживает. Сами файлы лежат на диске или в системе хранения.

Для PVC `database-data` Kubernetes ищет свободный PV класса `fast`, объёмом не меньше `2Gi` и с режимом `ReadWriteOnce`. Если подходящий PV уже есть, Kubernetes связывает его с заявкой.

Если готового PV нет, provisioner из StorageClass `fast` создаёт хранилище и описывающий его PV. Новый PV тоже получает `storageClassName: fast`, после чего Kubernetes связывает его с PVC. Это называется **динамическим предоставлением хранилища**.

Связанные PVC и PV получают состояние **`Bound`**. Один PVC связывается с одним PV, и этот PV закрепляется за ним.

Если в StorageClass задан `volumeBindingMode: WaitForFirstConsumer`, подбор или создание тома откладывается до появления Pod из следующего шага. Так Kubernetes учитывает, на каком узле сможет работать приложение. До этого PVC может оставаться `Pending` — ждать обработки заявки.

## Шаг 4. Pod подключает хранилище через PVC

Теперь в Pod укажем заявку `database-data`, а в контейнере выберем папку `/data` для её хранилища:

```yaml
# storage-demo.yaml — продолжение: Pod
---
apiVersion: v1
kind: Pod
metadata:
  name: storage-demo
  namespace: study
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "while true; do sleep 3600; done"] # Пауза на час в цикле, чтобы контейнер работал
      volumeMounts:
        - name: data       # Подключить том data из volumes
          mountPath: /data # Папка, которую увидит приложение
  volumes:
    - name: data           # Имя тома внутри Pod
      persistentVolumeClaim:
        claimName: database-data # Имя PVC из шага 2
```

При запуске Pod Kubernetes подключает хранилище связанного PV. Приложение работает с ним как с обычной папкой `/data`. Файл, записанный туда, попадёт в это хранилище.

```text
/data в контейнере → том data в Pod → PVC database-data → связанный PV → хранилище
```

Pod использует PVC из своего namespace — здесь это `study`. PV и StorageClass существуют на уровне кластера.

## Шаг 5. Новый Pod использует прежние данные

Если удалить Pod `storage-demo`, отдельный PVC `database-data`, связанный PV и файлы останутся. Новый Pod указывает тот же `claimName: database-data` и получает доступ к прежнему хранилищу.

Так работает и Pod из Deployment. StatefulSet помогает управлять хранилищем отдельных реплик — эту задачу разбираем в [записи 14](14_statefulset_headless_service.md).

## Если хранилище уже подготовлено

Администратор может заранее подготовить диск или сетевую папку и создать PV с её описанием. Тогда Kubernetes подберёт этот PV для подходящего PVC. Это называется **статическим предоставлением хранилища**. Provisioner для создания такого тома не нужен.

При подборе должны подходить класс, объём и режим доступа. Например, свободный PV класса `fast` на `5Gi` с режимом `ReadWriteOnce` подходит нашей заявке на `2Gi`. За PVC закрепится весь PV.

## Если StorageClass в PVC не указан

В основном примере мы явно выбрали `fast`. Два других варианта имеют разный смысл:

- **Поле `storageClassName` пропущено:** Kubernetes может назначить класс по умолчанию, если он настроен в кластере.
- **Указано `storageClassName: ""`:** PVC запрашивает готовый PV без класса. Класс по умолчанию для этой заявки использоваться не будет.

## Сколько Pod могут использовать один PVC

Режим доступа из `accessModes` задаёт требования к подключению хранилища:

| Режим | Сокращение | Доступ |
|---|---|---|
| `ReadWriteOnce` | RWO | Чтение и запись с одного Node |
| `ReadOnlyMany` | ROX | Чтение с нескольких Node |
| `ReadWriteMany` | RWX | Чтение и запись с нескольких Node |
| `ReadWriteOncePod` | RWOP | Использование одним Pod во всём кластере |

В нашем примере `ReadWriteOnce` позволяет нескольким Pod на одном узле использовать тот же PVC. Если требуется доступ только одному Pod во всём кластере, выбирают `ReadWriteOncePod`.

Поддержка режимов зависит от системы хранения и её драйвера. Для `ReadWriteOncePod` нужен совместимый **CSI-драйвер** — компонент, который подключает систему хранения через стандартный интерфейс Kubernetes.

Режимы учитываются при подборе PV. Чтобы запретить запись через конкретное подключение тома, задают `volumeMounts[].readOnly: true`. Согласованную запись нескольких процессов в общие файлы обеспечивает приложение.

## Что произойдёт после удаления PVC

При удалении PVC дальнейшая судьба тома зависит от поля `persistentVolumeReclaimPolicy` у PV:

| Политика | Что останется после удаления PVC |
|---|---|
| `Retain` | PV и данные сохранятся. Администратор сможет подготовить том к повторному использованию |
| `Delete` | Реализация, поддерживающая удаление, удалит PV и соответствующее хранилище |

При автоматическом создании PV получает эту политику из `reclaimPolicy` StorageClass. Если она не задана, по умолчанию используется `Delete`.

При `Retain` PV обычно переходит в состояние `Released`: прежняя заявка удалена, но том ещё нужно подготовить для нового PVC.

## Основные команды

```bash
# Посмотреть классы и настройки выбранного класса
kubectl get storageclass
kubectl describe storageclass fast

# Найти PV, связанный с заявкой
kubectl get pvc database-data -n study -o wide
kubectl get pv

# Посмотреть поля объектов и причины ошибок
kubectl get pvc database-data -n study -o yaml
kubectl describe pvc database-data -n study
kubectl describe pv PV_NAME
kubectl describe pod storage-demo -n study
```

`PV_NAME` — имя из колонки `VOLUME` у PVC. У PV нет namespace, поэтому команда для него выполняется без `-n`.

## Если хранилище не подключается

Проверяй цепочку из примера: Pod → PVC → PV → хранилище. Состояния объектов и Events помогают понять, на каком шаге возникла проблема.

| Наблюдение | Что проверить |
|---|---|
| Pod не находит PVC | Имя в `claimName`, существование PVC и совпадение namespace |
| PVC остаётся `Pending` | Выбранный класс, подходящие свободные PV и работу provisioner. При `WaitForFirstConsumer` сначала нужен Pod |
| PVC уже `Bound`, но Pod не запускается | Events Pod: ошибки подключения, ограничения узла или зоны |
| Приложение запущено, но файлов нет | Тот ли PVC подключён и пишет ли приложение в `/data` |
| Запись запрещена | Права на папку и `readOnly` у подключения тома |

`Bound` означает, что PVC связан с PV. Подключение хранилища к узлу — следующий этап, на котором тоже может возникнуть ошибка.

## Особый случай: блочный том

В примере контейнер получает папку с файловой системой. Это режим `volumeMode: Filesystem`, который используется по умолчанию. Для приложений, работающих напрямую с блочным устройством, есть `volumeMode: Block` и подключение через `volumeDevices`.

</details>

<details>
<summary>Показать ответ</summary>

Хранилище и объект PV с его описанием.

</details>

**3. Как Pod выбирает PVC, который нужно подключить?**

<details>
<summary>Показать ответ</summary>

</details>

**4. Pod удалили, но PVC оставили. Как новому Pod получить прежние файлы?**

<details>
<summary>Показать ответ</summary>

Подключить тот же PVC и читать файлы из подключённого тома.

</details>

**5. Чем отличается отсутствие `storageClassName` от `storageClassName: ""`?**

<details>
<summary>Показать ответ</summary>

Без поля может быть назначен класс по умолчанию. Пустая строка запрашивает PV без класса.

</details>

**6. Несколько Pod работают на одном Node. Могут ли они использовать один PVC с `ReadWriteOnce`?**

<details>
<summary>Показать ответ</summary>

Да. Этот режим ограничивает подключение одним Node.

</details>

**7. У класса задан `WaitForFirstConsumer`, а PVC остаётся `Pending`. Какой объект нужен для продолжения?**

<details>
<summary>Показать ответ</summary>

Pod, который использует этот PVC.

</details>

**8. Удалили PVC, а у PV задано `Retain`. Что произойдёт с данными?**

<details>
<summary>Показать ответ</summary>

Данные сохранятся. Подготовить том к повторному использованию сможет администратор.

</details>
