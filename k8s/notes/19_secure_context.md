# 19. SecurityContext: права процесса и доступ к файловой системе

## Какую проблему решаем

В [записи 18](18_rbac.md) мы ограничивали действия клиента в Kubernetes API. **`securityContext` задаёт права процесса внутри контейнера:** от какого Linux-пользователя он работает, куда может писать и какие привилегированные операции выполнять. Здесь рассматриваем Linux-контейнеры на Linux-узлах.

## Пример: запуск без root и рабочий каталог

Запустим BusyBox без root. Корневую файловую систему сделаем доступной только для чтения, а для записи подключим `emptyDir` в `/work`.

**UID — числовой идентификатор пользователя, GID — группы.** Для примера выбраны UID `1000`, основная группа с GID `3000` и дополнительная группа с GID `2000` для доступа к тому. Эти числа выбраны произвольно, специальных значений в Kubernetes у них нет. UID `0` означает root.

```yaml
# security-context-demo.yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-context-demo
  namespace: study
spec:
  nodeSelector:
    kubernetes.io/os: linux
  securityContext:        # Общие настройки Pod
    runAsUser: 1000        # Запустить процесс от пользователя с UID 1000
    runAsGroup: 3000       # Основная группа процесса с GID 3000
    runAsNonRoot: true     # Требовать UID, отличный от 0
    fsGroup: 2000          # Дополнительная группа с GID 2000 для доступа к тому
    seccompProfile:
      type: RuntimeDefault # Стандартный фильтр системных вызовов
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "while true; do sleep 3600; done"] # Пауза на час в цикле, чтобы контейнер продолжал работать
      securityContext:    # Настройки этого контейнера
        privileged: false # Обычный режим контейнера
        allowPrivilegeEscalation: false # Запретить получение дополнительных привилегий
        readOnlyRootFilesystem: true # Корневая файловая система только для чтения
        capabilities:
          drop:
            - ALL # Убрать все Linux capabilities
      volumeMounts:
        - name: work
          mountPath: /work # Рабочий каталог с доступом для записи
  volumes:
    - name: work
      emptyDir: {} # Временный том на срок жизни Pod
```

## Два уровня: Pod и контейнер

`spec.securityContext` задаёт общие настройки для контейнеров Pod и права томов. `spec.containers[].securityContext` — настройки конкретного контейнера. Если поле задано на обоих уровнях, значение контейнера имеет приоритет.

`fsGroup` задают только у Pod. `capabilities`, `allowPrivilegeEscalation` и `readOnlyRootFilesystem` — только у контейнера. В Deployment оба уровня находятся внутри `spec.template.spec`. Изменение шаблона запускает rollout, как в [записи 6](06_rollout.md).

## Пользователь и группы: runAsUser, runAsGroup и fsGroup

**`runAsUser` задаёт пользователя процесса, `runAsGroup` — его основную группу.** В примере это UID `1000` и GID `3000`. `runAsNonRoot: true` требует запуска с UID, отличным от `0`. Если выбран root, kubelet отклонит запуск.

**`fsGroup: 2000` добавляет процессам Pod группу `2000` и помогает подготовить права тома.** В примере Kubernetes назначает `emptyDir` группу `2000` и разрешает ей запись. Каталог имеет бит **setgid**: новые файлы наследуют его группу. Поэтому файл в `/work` получит UID `1000` и GID `2000`, хотя основная группа процесса — `3000`.

Смена UID сама по себе не меняет владельцев файлов в образе. Доступ зависит от пользователя, групп и прав файла. `fsGroup` работает с поддерживаемыми томами, а для PVC его поддержка зависит от драйвера хранилища.

## Привилегии: capabilities и allowPrivilegeEscalation

**Linux capabilities — отдельные привилегии процесса.** Например, `NET_ADMIN` позволяет менять сетевые настройки. `capabilities.drop: [ALL]` убирает все такие привилегии. Читать доступные файлы и писать в разрешённые каталоги процесс по-прежнему может.

**`allowPrivilegeEscalation: false` запрещает получать дополнительные привилегии при запуске другой программы.** Это включает Linux-флаг `no_new_privs`. Например, процесс не сможет повысить права через setuid — запуск программы с правами владельца её файла.

`privileged: true` включает привилегированный режим, который существенно расширяет доступ контейнера и ослабляет изоляцию. В примере задано `false`.

## Файловая система: readOnlyRootFilesystem и том

**`readOnlyRootFilesystem: true` запрещает запись в корневую файловую систему контейнера.** Поэтому в примере запись в `/tmp` завершится ошибкой.

В `/work` подключён отдельный том, и запись в него разрешена. Для тома действуют его собственные права и настройки подключения. `volumeMounts[].readOnly: true` сделает такое подключение доступным только для чтения.

`emptyDir` хранит данные на срок жизни Pod, как в [записи 12](12_volumes.md). Настройки прав доступа этот срок не меняют.

## Seccomp: фильтрация системных вызовов

**Системный вызов, или syscall, — обращение процесса к ядру Linux**, например для открытия файла. `seccompProfile` выбирает профиль фильтрации таких вызовов. `type: RuntimeDefault` включает стандартный профиль container runtime. Конкретные правила зависят от runtime.

## Если контейнер не запускается или запись запрещена

Как в [записи 3](03_debug.md), сначала проверь Events Pod, затем логи запущенного контейнера и фактические права.

```bash
kubectl describe pod security-context-demo -n study
kubectl logs security-context-demo -n study -c app
kubectl get pod security-context-demo -n study -o yaml
```

| Наблюдение | Что проверить |
|---|---|
| API отклоняет манифест из-за неизвестного поля | Уровень поля: Pod или контейнер. Написание и версию API |
| Events сообщают о нарушении `runAsNonRoot` | Эффективный UID: настройки контейнера, Pod и пользователь образа |
| Приложение завершается с `Permission denied` | UID, группы, владельца и режим нужного файла или каталога |
| Запись завершается с `Read-only file system` | Корневую файловую систему и `readOnly` у подключения тома |
| `fsGroup` задан, но запись в PVC не работает | Поддержку драйвера, фактические права и доступность подключения для записи |
| После включения seccomp запрещена операция | Какой syscall нужен приложению и какое правило профиля его ограничивает |
| API отклоняет создание из-за политики безопасности | Сообщение admission и требования политики namespace |

## Особые случаи

- Если пользователь образа указан именем, kubelet может отклонить запуск с `runAsNonRoot`, когда его UID неизвестен. Явный числовой `runAsUser` устраняет неопределённость.
- Для privileged-контейнера или процесса с `CAP_SYS_ADMIN` `allowPrivilegeEscalation` всегда считается включённым.
- **Pod Security** — политики, проверяющие настройки при создании Pod. Например, профиль Restricted требует non-root, запрет повышения привилегий и подходящий seccomp-профиль.

## Проверь себя

**1. Приложению разрешено читать Secret через RBAC. Запустится ли оно из-за этого как root?**

<details>
<summary>Показать ответ</summary>

Нет. RBAC регулирует запросы к API. Linux-пользователь процесса определяется образом и настройками запуска, включая securityContext.

</details>

**2. Указали только `runAsNonRoot: true`, а образ запускается с UID 0. Kubernetes автоматически выберет UID 1000?**

<details>
<summary>Показать ответ</summary>

Нет. `runAsNonRoot` проверяет требование. Контейнер с UID 0 не запустится. Для выбора пользователя нужен `runAsUser` с подходящим ненулевым UID.

</details>

**3. У Pod `runAsUser: 1000`, у контейнера app `runAsUser: 1001`. С каким UID запустится app?**

<details>
<summary>Показать ответ</summary>

`app` запустится с UID `1001`: его настройка имеет приоритет.

</details>

**4. Задано `allowPrivilegeEscalation: false`. Каким полем убрать уже имеющиеся capabilities?**

<details>
<summary>Показать ответ</summary>

`capabilities.drop: [ALL]`. Запрет повышения привилегий и набор уже имеющихся capabilities задаются отдельно.

</details>

**5. Задано `readOnlyRootFilesystem: true`. Почему в примере запись в `/tmp` запрещена, а в `/work` разрешена?**

<details>
<summary>Показать ответ</summary>

В примере /tmp принадлежит корневой файловой системе, доступной только для чтения. В /work подключён отдельный emptyDir с доступом для записи и подходящими правами.

</details>

**6. Чем отличаются `runAsGroup: 3000` и `fsGroup: 2000`?**

<details>
<summary>Показать ответ</summary>

`runAsGroup` задаёт основную группу процесса — `3000`. `fsGroup` добавляет группу `2000` и участвует в подготовке прав поддерживаемых томов.

</details>

**7. Что включает `seccompProfile.type: RuntimeDefault`?**

<details>
<summary>Показать ответ</summary>

Стандартный профиль фильтрации системных вызовов container runtime.

</details>

**8. В `/work` успешно записали файл. Что произойдёт с ним после удаления Pod из примера?**

<details>
<summary>Показать ответ</summary>

Файл исчезнет: в `/work` подключён `emptyDir`. Права, заданные через `fsGroup`, определяют доступ, а срок жизни данных зависит от источника тома.

</details>
