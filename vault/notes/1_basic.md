# Основы Vault

## 1. Что такое Vault

**HashiCorp Vault** - система централизованного управления секретами (*Secrets Management*), позволяющая безопасно хранить, генерировать, выдавать и отзывать чувствительные данные.

К секретам относятся пароли БД, API-ключи, токены, TLS-сертификаты, SSH-ключи и другие credentials.

**Основные возможности:**
- **Централизация** - единое управление секретами для Kubernetes, VM, CI/CD и других систем.
- **Контроль доступа** - аутентификация клиентов и авторизация через Policies.
- **Динамические секреты** - генерация временных credentials с ограниченным сроком действия.
- **Ротация** - обновление credentials и управление их жизненным циклом.
- **Аудит** - регистрация обращений к Vault API.
- **Шифрование** - защита хранимых данных и криптографические операции.

Vault дополняет Kubernetes Secrets и другие механизмы хранения секретов, предоставляя централизованное управление доступом и дополнительные возможности автоматизации.

## 2. Архитектура и принцип работы

**Vault Server - HTTP-сервер с API**, к которому клиенты обращаются напрямую или через Vault CLI, SDK и интеграции.

```text
                      CLIENT
                  (CLI / API / Agent)
                         │
                         │ HTTP(S)
                         ▼
                 ┌─────────────────┐
                 │  VAULT SERVER   │
                 │                 │
                 │  Auth Methods   │
                 │       ↓         │
                 │  Vault Token    │
                 │       ↓         │
                 │    Policies     │
                 │       ↓         │
                 │ Secrets Engines │
                 │       ↓         │
                 │     Storage     │
                 └─────────────────┘
```

### Основные компоненты

| Компонент | Назначение |
|---|---|
| **Auth Method** | Механизм аутентификации клиента |
| **Token** | Средство доступа к Vault API |
| **Policy** | Правила авторизации: разрешенные операции и пути |
| **Secrets Engine** | Модуль хранения, генерации или обработки секретов |
| **Storage Backend** | Хранилище состояния Vault |

### Последовательность работы

**1. Аутентификация**

Клиент обращается к Auth Method и подтверждает свою личность: например, через Kubernetes JWT, AppRole или OIDC. При успешной аутентификации Vault обычно выдает собственный токен.

**2. Авторизация**

Клиент выполняет запрос с Vault Token. Сервер проверяет действительность токена и разрешения из Policies.

**3. Выполнение операции**

Если доступ разрешен, соответствующий Secrets Engine обрабатывает запрос: читает секрет, генерирует credentials, выпускает сертификат и т. д.

**Главный принцип:**

```text
Authentication → Token → Policy → Secrets Engine
```

Auth Method отвечает на вопрос **«Кто ты?»**, Policy - **«Что тебе разрешено?»**, Secrets Engine - **«Как выполнить операцию?»**.

## 3. Auth Methods, Tokens и Policies

### Auth Methods

**Auth Method** - механизм проверки личности клиента для получения Vault Token. Vault предоставляет такие реализации: 

- `token` - прямое использование Vault-токена
- `kubernetes` - аутентификация приложений через ServiceAccount JWT
- `approle` - машинная аутентификация через RoleID и SecretID
- `jwt` - аутентификация через JWT, например в CI/CD
- `oidc` - аутентификация пользователей через Identity Provider
- `ldap` - интеграция с корпоративными каталогами
- `aws` - аутентификация AWS workloads

Сами Auth Methods подключаются к определенным API-путям, например `auth/kubernetes/`.

### Vault Token

**Vault Token** - секретный токен, который клиент предъявляет при обращении к Vault API. С этим токеном связаны:

- **Policies** - разрешенные действия.
- **TTL** - оставшееся время действия.
- **Renewable** - возможность продления.
- **Accessor** - идентификатор для управления токеном без раскрытия его значения.

После успешной аутентификации клиент использует Vault Token для дальнейших запросов, без необходимости повторно предъявлять исходные credentials перед каждой операцией.

Есть особенный токен - **root token**. Он обладает административными полномочиями и предназначен для админа, поэтому не должен использоваться приложениями. 

### Policies

**Policy** - набор правил авторизации, описывающих разрешенные операции над API-путями Vault. Vault использует принцип **deny by default**: операция запрещена, если применимые Policies ее не разрешают.

Основные capabilities (возможности):

- `create`
- `read`
- `delete`
- `update` - изменить
- `put` - частично измененить
- `list` - получить список
- `sudo` - отдельные привилегированные операции

Пример HCL-политики:

```hcl
path "secret/data/myapp" {
  capabilities = ["read"]
}
```

Эта политика разрешает читать секрет `myapp` из KV v2.

**Важные особенности:**

- Policies могут назначаться токенам или через Identity.
- Изменение существующей Policy обычно применяется к уже выданным токенам без их перевыпуска.
- Удаление Policy не означает автоматического отзыва токенов, которым она была назначена.
- Отзыв токена (*revocation*) делает недействительным сам токен.

### Roles

**Role** - именованная конфигурация внутри определенного Auth Method или Secrets Engine.

Ее назначение зависит от компонента:

- **Kubernetes Auth Role** - определяет допустимые ServiceAccounts и назначаемые Policies.
- **AppRole** - конфигурация машинной аутентификации.
- **Database Role** - определяет правила генерации credentials для БД.

Важно: **Role и Policy - не одно и то же**. Policy отвечает за разрешения, а назначение Role зависит от механизма, которому она принадлежит.

## 4. Secrets Engines

**Secrets Engine** - подключаемый модуль Vault, который хранит, создает или обрабатывает секреты. Vault предоставляет такие реализации:

- **KV** - хранение статических секретов
- **Database** - генерация и управление credentials баз данных
- **SSH** - управление SSH-доступом
- **PKI** - выпуск и управление сертификатами
- **Transit** - криптографические операции без передачи ключей клиенту
- **AWS** - выдача AWS credentials

Каждый экземпляр Secrets Engine подключается по определенному пути **mount path**.

Например:

```text
Vault
├── secret/       → KV v2
├── database/     → Database Engine
└── pki/          → PKI Engine
```

**Mount Path** - адрес подключения движка внутри Vault API, а не директория файловой системы.

Несколько экземпляров одного движка могут существовать одновременно с разными настройками и путями.

### Статические и динамические секреты

- **Static Secrets** - заранее созданные значения, которые Vault хранит и выдает клиентам. Пример: пароль приложения в KV v2.
- **Dynamic Secrets** - credentials, генерируемые по запросу с ограниченным сроком действия. Пример: Vault подключается к PostgreSQL, создает временного пользователя и выдает его credentials приложению.

Главное отличие: **динамические секреты позволяют Vault управлять доступом непосредственно во внешней системе**, включая отзыв credentials.

## 5. KV Secrets Engine

**KV (Key-Value)** - движок для хранения произвольных секретов в формате ключ-значение.

Существует две версии:

| KV v1 | KV v2 |
|---|---|
| Хранит актуальное значение | Поддерживает историю версий |
| Перезаписывает предыдущие данные | Сохраняет предыдущие версии в пределах настроенного лимита |
| Нет встроенного восстановления версий | Поддерживает soft delete и undelete |
| Нет версионирования CAS | Поддерживает CAS |

### Операции KV v2

| Команда | Назначение |
|---|---|
| `put` | Полностью записать или заменить данные секрета |
| `patch` | Частично обновить поля |
| `get` | Прочитать секрет |
| `list` | Получить список ключей |
| `metadata get` | Получить метаданные и историю версий |
| `delete` | Пометить версию удаленной |
| `undelete` | Восстановить soft-deleted версию |
| `destroy` | Безвозвратно уничтожить данные версии |
| `metadata delete` | Удалить все версии и метаданные секрета |

**`put` и `patch` создают новую версию данных**, тогда как `delete` и `undelete` меняют состояние существующей версии.

`destroy` уничтожает данные указанной версии без возможности восстановления через Vault.

### Особенность API-путей KV v2

Vault CLI использует упрощенные пути:

```bash
vault kv get secret/myapp
```

Однако фактический HTTP-запрос обращается к:

```http
GET /v1/secret/data/myapp
```

Здесь:
- `/v1/` - префикс HTTP API Vault.
- `secret/` - mount path KV Engine.
- `data/` - API-путь KV v2 для операций с данными.
- `myapp` - путь самого секрета.

Поэтому в Policies используется:

```hcl
path "secret/data/myapp" {
  capabilities = ["read"]
}
```

Для операций с метаданными KV v2 используется другой API-путь - `secret/metadata/myapp`.

Это важно учитывать при настройке прав доступа.

## 6. TTL, Lease и Revocation

Для управления временем жизни токенов и выдаваемых credentials есть такие понятия:

| Термин | Значение |
|---|---|
| **TTL** (time to live, время жизни) | Время, оставшееся до истечения срока действия |
| **Lease** (аренда) | Управляемая аренда выданного секрета |
| **Renewal** (обновление)  | Продление срока действия |
| **Revocation** (отзыв/отмена) | Отзыв токена или выданных credentials |

### TTL токенов

Например, токен создан на 24 часа:

```text
creation_ttl = 24h
ttl          = 23h
renewable    = true
```

`creation_ttl` - первоначально выданный срок, `ttl` - оставшееся время.

`renewable=true` означает, что токен допускает продление, но фактическая возможность продления зависит от настроенных ограничений.

### Lease динамических секретов

Пример PostgreSQL:

```text
1. Приложение запрашивает credentials
              ↓
2. Vault создает пользователя PostgreSQL
              ↓
3. Возвращает username + password + lease_id
              ↓
4. Lease действует ограниченное время
              ↓
5. Vault продлевает или отзывает credentials
```

При отзыве Vault выполняет предусмотренную движком процедуру отзыва доступа, например удаляет пользователя из PostgreSQL.

**Важно:** TTL Vault-токена и TTL динамического секрета - независимые параметры.

Истечение Vault-токена не означает автоматического уничтожения всех ранее прочитанных статических паролей.

Статические секреты KV v2 сами по себе не становятся недействительными из-за TTL клиентского токена.

## 7. Vault CLI - основные команды

Vault CLI - клиент для обращения к Vault HTTP API.

### Подключение и состояние

```bash
# Адрес сервера
export VAULT_ADDR=http://127.0.0.1:8200

# Аутентификация
vault login

# Состояние Vault
vault status
```

### Secrets Engines

```bash
# Список движков
vault secrets list

# Подробная информация
vault secrets list -detailed

# Включение KV v2
vault secrets enable -path=secret kv-v2

# Включение Database Engine
vault secrets enable database
```

### Работа с KV v2

```bash
# Создание
vault kv put secret/myapp username=admin password=test123

# Чтение
vault kv get secret/myapp

# Чтение отдельного поля
vault kv get -field=password secret/myapp

# Обновление отдельного поля
vault kv patch secret/myapp password=new123

# Чтение конкретной версии
vault kv get -version=1 secret/myapp

# Метаданные и версии
vault kv metadata get secret/myapp

# Soft delete текущей версии
vault kv delete secret/myapp

# Восстановление версии
vault kv undelete -versions=1 secret/myapp

# Безвозвратное уничтожение версии
vault kv destroy -versions=1 secret/myapp
```

### Auth Methods

```bash
# Доступные методы
vault auth list

# Включение Kubernetes Auth
vault auth enable kubernetes

# Включение AppRole
vault auth enable approle
```

### Policies

```bash
# Список
vault policy list

# Чтение
vault policy read myapp-policy

# Создание или обновление
vault policy write myapp-policy policy.hcl

# Удаление
vault policy delete myapp-policy
```

### Tokens

```bash
# Информация о текущем токене
vault token lookup

# Создание токена
vault token create -policy=myapp-policy

# Просмотр через accessor
vault token lookup -accessor <accessor>

# Продление текущего токена
vault token renew

# Отзыв через accessor
vault token revoke -accessor <accessor>
```

**Безопасность:** не передавать реальные пароли и токены в аргументах команд без необходимости - они могут попасть в shell history, журналы или список процессов. Для автоматизации предпочтительны защищенные механизмы передачи секретов.

## 8. Production: архитектура и эксплуатация

### Seal / Unseal (запечатанные/вскрытые)

Vault шифрует хранимые данные и использует механизм блокировки доступа к ним.

- **Initialized** - Vault инициализирован, создан необходимый ключевой материал.
- **Sealed** - Vault заблокирован и не может обслуживать обычные запросы к секретам.
- **Unseal** - разблокировка Vault.
- **Auto-unseal** - автоматическая разблокировка с использованием внешнего KMS/HSM или другого поддерживаемого механизма.

### Storage Backend

Vault требует хранилище для своего состояния: секретов, Policies, конфигурации и других данных.

- **Dev Mode (`inmem`)** хранит данные в памяти. При перезапуске процесса Vault состояние теряется.
- **Integrated Storage (Raft)** - встроенное постоянное распределенное хранилище Vault.

### High Availability

В production Vault обычно разворачивают с несколькими серверами.

При использовании Integrated Storage данные реплицируются через Raft, а обработка операций координируется активным узлом Vault.

Для отказоустойчивости важны:
- Несколько Vault Server.
- Корректная конфигурация Raft.
- Сохранение кворума.
- Постоянное хранилище.
- Правильно настроенный Auto-unseal.
- Резервное копирование и проверка восстановления.

### Безопасность и эксплуатация

**Основные рекомендации:**

- Использовать TLS для Vault API.
- Не использовать root-токен в приложениях.
- Придерживаться принципа минимальных привилегий.
- По возможности использовать workload identity вместо статических Vault-токенов.
- Настраивать Audit Devices.
- Контролировать TTL и жизненный цикл credentials.
- Настраивать мониторинг доступности, состояния seal, Raft и ошибок.
- Регулярно проверять backup и restore.
- Учитывать зависимость приложений от доступности Vault.

**Важный нюанс:** недоступность Vault не обязательно немедленно останавливает работающие приложения. Все зависит от того, получили ли они секреты ранее, нужны ли им новые credentials и как реализовано обновление конфигурации.

## Саммари

**Vault - это HTTP-сервер для централизованного управления секретами.**

Его базовая модель:

```text
Auth Method → Token → Policy → Secrets Engine
```

- **Auth Method** - устанавливает личность клиента.
- **Token** - используется для доступа к API.
- **Policy** - определяет разрешенные операции.
- **Secrets Engine** - хранит, генерирует или обрабатывает секреты.
- **Storage Backend** - обеспечивает хранение состояния Vault.
- **TTL / Lease / Revocation** - управляют жизненным циклом доступа и credentials.

Ключевое отличие Vault от простого хранилища паролей - **возможность централизованно контролировать доступ и автоматически управлять временными credentials внешних систем**.
